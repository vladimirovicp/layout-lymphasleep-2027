# Compound Engineering: Brainstorm → Plan → Work

Руководство для **OpenCode 2.x** по актуальной документации [EveryInc/compound-engineering-plugin](https://github.com/EveryInc/compound-engineering-plugin). Названия команд относятся к текущей линейке `ce-*`; при использовании закреплённой старой версии сверяйтесь с её документацией.

## Что это такое

**Compound Engineering** — подход к разработке с ИИ, при котором каждая выполненная задача должна облегчать следующие. Агент не только пишет код, но и уточняет требования, фиксирует решения, проверяет результат и сохраняет полезные выводы в проекте.

Одноимённый плагин от Every предоставляет набор **skills** — инструкций для агента — и команд для выполнения этих этапов. Это не отдельная модель и не MCP-сервер: он организует работу модели и инструментов, доступных в OpenCode.

Ключевая идея: знания не должны оставаться только в переписке. Понятный план, проверяемые критерии и запись о неочевидной проблеме становятся контекстом для следующей задачи.

## Основной цикл

```text
Brainstorm → Plan → Work → Simplify → Review → Compound
     ↑                                            │
     └────── следующая задача использует выводы ────┘
```

Первые три этапа отвечают на разные вопросы:

| Этап | Команда | Главный вопрос | Результат |
| --- | --- | --- | --- |
| Brainstorm | `/ce-brainstorm` | Что именно нужно получить и зачем? | Согласованные требования и границы задачи |
| Plan | `/ce-plan` | Какие решения, части работы и проверки нужны? | План, готовый к реализации |
| Work | `/ce-work` | Как реализовать согласованное в этом коде? | Изменения, проверки и отчёт; обычно также коммиты и PR |

### 1. Brainstorm — определить задачу

Используйте, когда идея ещё расплывчата: «нужна форма записи», «сделай удобнее», «добавим уведомления».

Агент уточняет цель и пользователей, задаёт вопросы по одному, рассматривает несколько вариантов и помогает выбрать объём работы. Важно согласовать не только то, что делаем, но и **то, что сейчас не делаем**.

Для обычной программной задачи результат сохраняется как план с требованиями в `docs/plans/`. В текущей версии это единый документ, который следующий этап дополняет, а не обязательно отдельный файл в `docs/brainstorms/`. Небольшое обсуждение может закончиться кратким итогом в чате без файла.

**Когда этап закончен:** понятны ожидаемое поведение, критерии приёмки, ограничения и выбранное направление. Реализацию пока не начинают.

### 2. Plan — подготовить реализацию

Агент изучает кодовую базу, существующие решения и накопленные знания в `docs/solutions/`. Затем фиксирует:

- технические решения и их причины;
- границы изменений и затрагиваемые файлы;
- части работы и зависимости между ними;
- тестовые сценарии с конкретными ожидаемыми результатами;
- риски и вопросы, блокирующие выполнение.

В текущей версии план — **не заранее написанный код и не жёсткий сценарий shell-команд**. Он задаёт решения и проверяемый результат, оставляя исполнителю выбор конкретной реализации с учётом кода.

Если Brainstorm уже создал документ с требованиями, `/ce-plan` дополняет этот же файл до состояния, пригодного для реализации. У частей работы могут быть стабильные идентификаторы `U1`, `U2` и т. д.

**Когда этап закончен:** нет неразрешённых вопросов, без которых нельзя безопасно начать, а выполнение каждой части можно проверить.

### 3. Work — реализовать и проверить

Агент читает готовый план, проверяет, что уже выполнено, реализует оставшиеся части и запускает проверки. Сам документ плана при выполнении остаётся неизменным; состояние работы определяется по коду, Git и трекеру задач.

Для небольшой понятной задачи `/ce-work` можно вызвать и без сохранённого плана. Но документ с одними требованиями ещё не готов для выполнения: сначала его нужно дополнить через `/ce-plan`.

**Важно:** самостоятельный `/ce-work` включает процесс подготовки результата к отправке. Он может создавать ветки и коммиты, выполнять упрощение и ревью, затем вызывать процесс отправки кода и создания PR. Не считайте его командой «только поменять файлы».

Для первого запуска заранее укажите ограничения: разрешены ли коммиты, `push`, PR, установка зависимостей и использование других моделей. Инструкция в запросе задаёт намерение, но не заменяет технические ограничения прав OpenCode.

## Почему трёх этапов недостаточно для накопления знаний

Brainstorm → Plan → Work структурирует отдельную задачу. Накопительный эффект появляется, когда полезные выводы возвращаются в проект:

| Команда | Назначение |
| --- | --- |
| `/ce-simplify-code` | Упростить свежие изменения, убрать ненужную сложность |
| `/ce-code-review` | Проверить изменения; по умолчанию подготовить отчёт без применения исправлений |
| `/ce-compound` | Сохранить важный урок в подходящей форме: тесте, правиле или документе в `docs/solutions/` |

Например, при работе над формой выяснилось, что повторный клик отправляет заявку дважды. Исправление решает текущую проблему. Регрессионный тест и, если нужно, описание неочевидной причины помогают не повторять расследование в других формах.

Не нужно создавать документ ради каждого изменения. `/ce-compound` оценивает, есть ли проверенное, неочевидное и долгосрочно полезное знание. Если всё уже понятно из кода и тестов, он может ничего не записывать.

В самостоятельном режиме `/ce-work` уже выполняет финальные проверки и ревью. Не нужно автоматически повторять их вручную, если они только что завершились и код с тех пор не изменился.

## Подключение к OpenCode

Ниже приведена инструкция, а не выполненная установка: сам этот Markdown-файл ничего не подключает.

### 1. Проверьте версию

В терминале:

```bash
opencode --version
```

Примеры ниже используют конфигурацию **OpenCode 2.x**.

### 2. Добавьте плагин в конфигурацию

Для текущего проекта добавьте запись в `opencode.jsonc` в корне репозитория:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "plugins": [
    "compound-engineering@git+https://github.com/EveryInc/compound-engineering-plugin.git"
  ]
}
```

Для всех проектов используйте глобальный файл `~/.config/opencode/opencode.jsonc` или `$XDG_CONFIG_HOME/opencode/opencode.jsonc`, если задан `XDG_CONFIG_HOME`.

Если конфигурация уже существует, **дополните массив `plugins`**, сохранив остальные настройки. Не добавляйте второй одноимённый JSON-ключ. В OpenCode 2.x используется `plugins` во множественном числе; это настройка `opencode.json(c)`, а не `cli.json`.

По официальной инструкции плагин сам регистрирует skills и slash-команды. Отдельный Bun-установщик, копирование skills или добавление MCP-сервера не нужны.

OpenCode 2.x автоматически подхватывает изменения конфигурации; недостающий пакет устанавливается в фоне. Дождитесь завершения установки, при необходимости выполните `/reload`. В инструкции самого CE встречается рекомендация перезапустить OpenCode; для обычного изменения конфигурации здесь используется поведение, описанное в документации OpenCode 2.x.

### 3. Проверьте команды и настройте проект

В интерфейсе OpenCode:

```text
/ce-help
```

Затем:

```text
/ce-setup
```

`/ce-setup` проверяет доступные возможности и конфигурацию проекта. В Git-репозитории он обновляет пример `.compound-engineering/config.example.yaml` и предлагает согласовать остальные настройки. Это не полностью read-only проверка: просмотрите появившиеся изменения.

Дополнительные инструменты зависят от сценария: например, `gh` нужен для GitHub-процессов, а браузерные проверки требуют подходящего браузерного инструмента. Отсутствие всех необязательных утилит не означает, что плагин сломан; `/ce-setup` не устанавливает их все автоматически.

### Воспроизводимость и обновления

Запись без Git-ref не закрепляет версию. Для команды полезно выбрать проверенный релиз из [списка релизов](https://github.com/EveryInc/compound-engineering-plugin/releases). По инструкции CE к Git-адресу добавляется суффикс `#compound-engineering-vX.Y.Z`, где `X.Y.Z` заменяется на **реально существующую версию**. Полный commit SHA обеспечивает более строгую фиксацию исходников, чем перемещаемый тег.

Перед обновлением проверяйте изменения команд и поведения. После обновления повторите `/ce-setup`; сохранённые инструкции и примеры также могут требовать актуализации.

## Пример: форма записи на сайте

Команды `/ce-*` вводятся **в интерфейсе OpenCode**, не в shell. Выполняйте их по очереди, дожидаясь результата и отвечая на вопросы.

### Шаг 1. Согласовать требования

```text
/ce-brainstorm Нужна форма записи на сайте: имя, телефон и согласие
на обработку данных. Уточни поведение и критерии приёмки.
Не начинай реализацию. Админка, оплата и SMS пока вне задачи.
```

Проверьте, что обсуждение охватило валидацию, состояние отправки, успешный ответ и ошибку. Не позволяйте агенту придумать существующий backend: способ отправки заявки должен быть согласован.

### Шаг 2. Подготовить план

```text
/ce-plan
```

В текущем разговоре команда использует согласованные требования. Между сессиями лучше явно передать **фактический путь**, который вернул предыдущий этап:

```text
/ce-plan docs/plans/<файл-плана>.md
```

Это шаблон пути, не готовое имя файла. Перед продолжением прочитайте план и проверьте объём изменений и сценарии тестирования.

### Шаг 3. Выполнить с явными ограничениями

```text
/ce-work docs/plans/<файл-плана>.md Реализуй согласованный план
и выполни доступные проверки. Не делай коммиты, push и PR.
Не устанавливай новые зависимости и не передавай работу другой модели
без отдельного согласования. В конце покажи изменения и результаты проверок.
```

Этот запрос намеренно ограничивает стандартный процесс отправки результата. Для строгого контроля дополнительно настройте права инструментов OpenCode. Не трактуйте отсутствие тестового окружения как успешное прохождение тестов.

### Шаг 4. Сохранить полезный вывод

После подтверждённого исправления неочевидной проблемы:

```text
/ce-compound Оцени урок из исправления повторной отправки формы.
Сохрани только подтверждённые выводы. Не делай коммиты, push и PR.
```

Если новых полезных знаний не было, этот шаг можно пропустить.

## Где хранятся результаты

Типичная структура; не все файлы обязательны:

```text
project/
├── opencode.jsonc
├── AGENTS.md
├── .compound-engineering/
│   ├── config.yaml           # общие настройки CE
│   ├── config.example.yaml   # пример настроек
│   └── config.local.yaml     # необязательные локальные переопределения
└── docs/
    ├── plans/                # требования и планы реализации
    └── solutions/            # накопленные полезные выводы
```

`opencode.jsonc` подключает плагин, `.compound-engineering/config.yaml` задаёт его настройки, а `AGENTS.md` содержит рабочие инструкции проекта. Это разные назначения.

По умолчанию артефакты находятся в `docs/`. Настройка CE `docs_root` позволяет изменить этот корень; она читается из общего `config.yaml`, а не из локального переопределения. Личные настройки `config.local.yaml` обычно исключают из Git. Не помещайте секреты в эти файлы или в планы.

## Как использовать вместе с Context7

Эти инструменты дополняют друг друга:

- **Compound Engineering** организует процесс: требования, план, реализация, проверка и накопление опыта.
- **Context7** предоставляет внешнюю документацию библиотек для исследования и реализации.

Например: «На этапе планирования проверь API по Context7 для версии зависимости из проекта; при отсутствии точной документации сообщи об этом». Подключение CE само по себе не устанавливает Context7.

Инструкция по подключению: [CONTEXT7.md](CONTEXT7.md).

## Когда применять и чего избегать

- **Неясная идея:** начните с Brainstorm.
- **Понятное ТЗ, несколько частей работы:** переходите сразу к Plan.
- **Маленькая очевидная правка:** полный цикл может стоить дороже самой задачи; выполните её напрямую или через Work.
- **Баг с неизвестной причиной:** сначала расследование; в плагине для этого есть `/ce-debug`.
- **Проверенное неочевидное открытие:** оцените необходимость Compound.

Не запускайте автономный `/lfg` при знакомстве с инструментом: это более широкий процесс, способный отправлять код, открывать PR и следить за CI. Сначала освойте последовательный цикл и задайте границы разрешённых действий.

Skills могут запускать исследовательских и проверяющих субагентов, что увеличивает расход токенов. Некоторые сценарии также могут использовать внешние agent CLI и других провайдеров. Для закрытого проекта заранее ограничьте такие передачи. Настройка `cross_model_review_mode: off` в CE отключает автоматический межмодельный проход ревью, но **не все внешние обращения**, не основной провайдер модели и не инструменты вроде Context7. Worktree также не является защитной песочницей.

## Если что-то не работает

| Проблема | Что проверить |
| --- | --- |
| Нет `/ce-help` или `/ce-plan` | Версию OpenCode, массив `plugins`, доступ к GitHub, завершение установки; затем `/reload` |
| Команды отличаются от статьи | Версию установленного CE и документацию именно этого релиза |
| Work не принимает план | Дополнен ли документ с требованиями через `/ce-plan`; устранены ли блокирующие вопросы |
| Не создаётся PR | Доступность и авторизацию GitHub-инструментов, remote и разрешение на отправку кода |
| Слишком долго или дорого | Размер задачи, объём исследования, число субагентов и необходимость полного цикла |
| Новая сессия не учитывает прошлые выводы | Сохранены ли они в проекте и доступны ли через согласованный каталог знаний |
