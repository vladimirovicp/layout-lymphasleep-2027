# Мини-курс: вёрстка научного журнала без backend

**Цель:** создать многостраничный адаптивный сайт научного журнала: общие шаблоны, архив выпусков, страницы статей, поиск и информационные страницы. Все данные локальные. Без API, базы данных, авторизации и серверной обработки форм.

**Рабочая среда:** OpenCode 2.x. **Учебный проект:** вымышленный научный журнал «Контур» об исследованиях окружающей среды и открытой науке.

Это руководство, а не уже установленное приложение. Примеры конфигурации и команды нужно выполнить в учебном проекте. В существующем проекте сначала изучите его настройки и не заменяйте их целиком.

## 1. Что создаём

### Конечный результат

- Статические HTML-страницы, CSS и небольшой клиентский JavaScript.
- Общие шапка, навигация, подвал, сетка и типографика.
- Повторно используемые компоненты вместо копирования разметки.
- Локальные демонстрационные статьи, авторы и выпуски.
- Рабочие внутренние переходы, мобильное меню, поиск и фильтр по локальным данным.
- Проверка на телефоне, планшете и широком экране.
- Папка `dist/`, которую можно разместить на обычном статическом хостинге.

**«Без сервера» здесь означает без backend приложения.** Для разработки и проверки используется локальный HTTP-сервер Astro. Это нормально: открывать собранный сайт через `file://` не нужно. Готовые HTML-файлы также обычно раздаёт статический HTTP-хостинг.

### Что не входит в первую версию

CMS, личные кабинеты, отправка рукописей, реальное рецензирование, рассылки, оплата, аналитика, интеграции с DOI/ORCID/Crossref, многоязычность и переключатель темы.

Не добавляем их «на будущее». Кнопку отправки статьи заменяем ссылкой на инструкцию для авторов. Форму связи, если она нужна для демонстрации, явно помечаем как не отправляющую данные.

### Карта страниц

| URL | Содержание | Основа |
| --- | --- | --- |
| `/` | Обложка текущего выпуска, краткое описание, избранные статьи | Главная |
| `/archive/` | Все выпуски, фильтр по году | Каталог |
| `/issues/2026-01/` | Выпуск № 1, аннотация, оглавление | Выпуск |
| `/articles/open-science-review/` | Статья, авторы, аннотация, текст, литература | Статья |
| `/search/` | Поиск по демонстрационным статьям | Каталог |
| `/about/` | О журнале и тематика | Информационная |
| `/editorial/` | Вымышленная редакционная коллегия | Информационная |
| `/for-authors/` | Учебные требования к рукописи | Информационная |
| `/contacts/` | Демонстрационные контакты, при желании локальная форма | Информационная |
| `/404.html` | Понятная ошибка и ссылки на главную/архив | Ошибка |

Другие выпуски и статьи создаются из данных по тем же шаблонам. Это **шесть типов страниц**, а не десять независимых дизайнов. Каталоги используют общий каркас, но не обязаны иметь одинаковые фильтры и карточки.

### Минимум данных для проверки

3 выпуска за 2 года, 12 статей, 4 вымышленных автора и 3 рубрики. Нужны длинный заголовок, несколько авторов, статья без иллюстрации и текст с таблицей. Красивые короткие заглушки не выявляют проблем вёрстки.

Все имена, публикации и реквизиты — учебные. На сайте разместите пометку «Демонстрационный сайт. Материалы и данные вымышлены». Не придумывайте настоящие DOI, ISSN, ORCID, научные индексы и сведения о рецензировании. Не копируйте чужие статьи и изображения без разрешения.

## 2. Стек, skills и MCP

### Рекомендуемый стек

**Astro + TypeScript + обычный CSS + локальные данные.**

Почему:

- Astro генерирует отдельные HTML-страницы: для журнала не нужен SPA-роутер.
- Шаблоны и компоненты убирают дублирование шапки, карточек и страниц.
- Большая часть сайта работает без клиентского JavaScript.
- CSS Grid, Flexbox и CSS-переменных достаточно для этого объёма.
- TypeScript помогает держать единые поля статей и компонентов.

Не устанавливаем одновременно React, Tailwind, UI-kit и библиотеку анимаций. Если рабочий проект уже построен на другом стеке, не переносите его на Astro только ради курса. Обычный HTML/CSS тоже подойдёт для нескольких страниц, но при большом числе статей ручное копирование шаблонов станет лишней работой.

### Чем отличаются инструменты

| Инструмент | Что даёт | Чего не делает |
| --- | --- | --- |
| Skill | Учит агента выполнять определённую работу | Не открывает браузер сам по себе |
| MCP | Даёт агенту доступ к инструментам, например браузеру | Не гарантирует хороший дизайн |
| `AGENTS.md` | Фиксирует правила именно этого проекта | Не устанавливает skills и MCP |
| Playwright Test | Запускает повторяемые тесты из файлов | Не равен браузерному MCP |

Строго обязательных внешних skills нет: сайт можно сделать и без них. Ниже — **минимальный рекомендуемый набор**, а не список всего, что следует установить.

### Skills

| Приоритет | Skill | Когда использовать |
| --- | --- | --- |
| Основной | `frontend-design` от Anthropic | Один раз выбрать визуальное направление; затем реализовать общую систему |
| Основной | `web-design-guidelines` от Vercel | Проверить готовые компоненты на доступность, UX и типовые ошибки |
| Полезный локальный | `journal-layout` — текст ниже | Не выходить за frontend-only объём и повторять один порядок работы |
| Необязательный | `ce-brainstorm`, `ce-plan`, `ce-work`, `ce-compound` | Если уже используете Compound Engineering или задача стала существенно сложнее |

`react-best-practices` нужен при использовании React, а не просто потому, что вы делаете frontend. Для данного Astro-проекта он не нужен. SEO-, deployment-, database- и backend-skills в первой версии также не нужны.

### MCP

| Приоритет | MCP | Польза |
| --- | --- | --- |
| Основной браузерный | Playwright MCP | Открывать локальный сайт, менять размер окна, нажимать элементы, делать скриншоты, смотреть ошибки |
| По необходимости | Context7 | Проверять конкретный API Astro или другой установленной зависимости |
| Альтернатива Playwright | Chrome DevTools MCP | Углублённо исследовать сеть, производительность и проблемы браузера |
| Только при наличии макета и доступа | Figma MCP | Получать контекст конкретного фрейма и ассеты |

**Начните с Playwright MCP.** Context7 подключите, когда действительно понадобится документация. Не включайте Playwright MCP и Chrome DevTools MCP одновременно без конкретной причины. Filesystem/GitHub/database MCP не нужны: файлы и Git уже доступны агенту, backend в задаче отсутствует.

## 3. Урок 1. Подготовить проект и инструменты

**Результат урока:** пустой Astro-проект открывается в браузере, два skills доступны, агент может проверить локальную страницу.

### Шаг 1. Проверить окружение

Потребуются OpenCode 2.x, Git, npm и поддерживаемая актуальной версией Astro версия Node.js LTS. На момент сверки страница установки Astro указывает Node.js **22.23.4 или новее**, без нечётных веток. Перед установкой проверьте [текущие требования](https://docs.astro.build/en/install-and-setup/).

В терминале, по отдельности:

```bash
node --version
npm --version
git --version
opencode --version
```

Для примера браузерного MCP ниже нужен установленный Google Chrome. Если работаете через SSH/контейнер, Chrome и его системные зависимости нужны именно там, где выполняется MCP; браузер вашего ноутбука не появится там автоматически.

### Шаг 2. Создать отдельный учебный проект

Запускайте мастер из каталога, в котором хотите создать **новую папку**, а не поверх существующей работы:

```bash
npm create astro@latest
```

В мастере выберите папку `science-journal`, минимальный/пустой шаблон и установку зависимостей. Если предлагается TypeScript — строгий режим. Не выбирайте готовую большую тему: изучение и удаление её ненужных возможностей часто дольше создания небольшого каркаса.

```bash
cd science-journal
```

Если мастер пропустил зависимости:

```bash
npm install
```

Добавьте проверку Astro/TypeScript:

```bash
npm install -D @astrojs/check typescript
```

В `package.json` дополните раздел `scripts`, сохранив остальные поля:

```json
{
  "scripts": {
    "dev": "astro dev",
    "check": "astro check",
    "build": "astro build",
    "preview": "astro preview"
  }
}
```

Это **фрагмент**, не полный `package.json`. Успешная сборка Astro сама по себе не заменяет `astro check`.

В `astro.config.mjs` задайте статический вывод:

```js
import { defineConfig } from 'astro/config';

export default defineConfig({
  output: 'static',
});
```

Адаптеры Node/Vercel/SSR не нужны. В `tsconfig.json` используйте `"extends": "astro/tsconfigs/strict"`, сохранив необходимые настройки созданного проекта.

Запустите:

```bash
npm run dev
```

Откройте URL, напечатанный в терминале, обычно `http://localhost:4321`. Оставьте процесс работающим; для OpenCode откройте второй терминал в **той же папке**. Если порт занят, используйте фактический адрес из вывода, а не вслепую повторяйте `4321`.

### Шаг 3. Установить только выбранные skills

Следующие команды используют сторонний CLI `skills`, а не встроенную команду OpenCode. Его актуальные требования также нужно учитывать; при указанной выше версии Node они покрываются.

```bash
npx skills add anthropics/skills --skill frontend-design -a opencode
```

```bash
npx skills add vercel-labs/agent-skills --skill web-design-guidelines -a opencode
```

Не добавляйте `-g`: здесь нужна установка в учебный проект. Посмотрите подтверждение установщика и файлы перед согласием; устанавливайте только названный skill. Сохраните созданный `skills-lock.json`, если установщик его создал.

Проверьте:

```bash
npx skills list
```

OpenCode читает project skills из `.opencode/skills/` и совместимых `.agents/skills/` / `.claude/skills/`. Фактическое размещение и ссылки зависят от установщика. Не создавайте несколько копий одного skill в разных каталогах.

В OpenCode можно явно запросить:

```text
Загрузи @frontend-design. Пока ничего не меняй.
Кратко подтверди, что skill доступен.
```

Если не появился — проверьте файлы, точный ID и права `skill`; при необходимости выполните `/reload`.

### Шаг 4. Подключить браузерный MCP

Создайте `opencode.jsonc` или дополните существующий:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "servers": {
      "playwright": {
        "type": "local",
        "command": [
          "npx",
          "-y",
          "@playwright/mcp@latest",
          "--browser",
          "chrome",
          "--headless",
          "--isolated"
        ]
      }
    }
  }
}
```

Здесь `--headless` позволяет работать без окна, а `--isolated` отделяет сессию от личного профиля браузера. Это не полноценная защитная песочница. Не подключайте профиль с личными аккаунтами.

`@latest` удобен для знакомства, но не фиксирует версию. Для повторяемого рабочего окружения после успешной проверки замените его на конкретную проверенную версию пакета. Аналогично фиксируйте версии остальных инструментов; не обновляйте их посреди этапа без необходимости.

Проверьте из терминала:

```bash
opencode mcp list
```

В интерфейсе OpenCode управление серверами доступно через `/mcps`. Конфигурация 2.x использует `mcp.servers`; старые примеры с `enabled` копировать не нужно. Изменения конфигурации подхватываются автоматически; при необходимости используйте `/reload`.

Проверочный запрос агенту:

```text
Через Playwright MCP открой http://localhost:4321.
Сообщи заголовок страницы и сделай один скриншот.
Ничего не устанавливай и не меняй. Если браузер или адрес недоступен,
покажи конкретную ошибку, а не утверждай, что проверка пройдена.
```

Если Chrome отсутствует, установите его по официальной инструкции вашей ОС или согласуйте другой поддерживаемый браузер и его установку. Не используйте `--no-sandbox` как универсальное решение. При первом запуске `npx` скачивает пакет; доступ в интернет нужен для настройки, но не для работы готового локального сайта.

### Шаг 5. Записать ограничения проекта

Создайте `AGENTS.md` в корне **учебного проекта**. Если он существует, добавьте правила без удаления прежних:

```markdown
# Правила учебного проекта

- Это frontend-only сайт научного журнала. Astro, TypeScript, обычный CSS.
- Только статический вывод. Без backend, API, БД, CMS, авторизации и SSR.
- Данные в src/data; изображения и шрифты локальные, с понятными лицензиями.
- Демонстрационные материалы явно помечены как вымышленные.
- Сначала согласовать краткий план текущего этапа; не реализовывать весь сайт сразу.
- Переиспользовать layouts и компоненты; не копировать шапку и карточки по страницам.
- Не менять утверждённые дизайн-токены без причины и согласования.
- Не добавлять библиотеки, MCP и новые функции без отдельного согласования.
- Формы ничего не отправляют; не показывать ложное сообщение об отправке.
- Использовать семантический HTML, видимый фокус и клавиатурную навигацию.
- Не скрывать переполнение всей страницы для маскировки ошибок вёрстки.
- В конце этапа показать изменённые файлы, проверки и реальные ограничения.
- Не делать коммиты, push, PR и публикацию без отдельной просьбы.
```

### Необязательный локальный skill

Если хотите закрепить последовательность работы, создайте `.opencode/skills/journal-layout/SKILL.md`. Это авторский шаблон для курса, не внешний готовый продукт:

```markdown
---
name: journal-layout
description: Вёрстка страниц учебного научного журнала на Astro без backend. Применять при создании шаблонов, страниц и адаптивных компонентов этого проекта.
---

1. Прочитай AGENTS.md и документы текущего этапа в docs/.
2. Уточни один измеримый результат и критерии приёмки. Не расширяй задачу.
3. Найди существующие tokens, layouts и компоненты; переиспользуй их.
4. Используй локальные типизированные данные. Не создавай API и серверные обработчики.
5. Реализуй один шаблон или одну связную группу компонентов за итерацию.
6. Проверь длинный контент, пустые результаты и отсутствие необязательных полей.
7. Выполни доступные проверки, затем проверь в браузере узкий и широкий экран.
8. Сообщи файлы, результаты проверок и блокеры. Не называй непроведённую проверку успешной.
9. Не запускай другие модели, публикацию, установку зависимостей и Git-запись без разрешения.
```

Вызов: «Используй `@journal-layout` для текущего этапа». Этот skill не заменяет визуальный дизайн или браузер, а предотвращает хаотичную последовательность действий.

**Переход к следующему уроку:** стартовая страница открывается и агент действительно получил скриншот. Не продолжайте при сломанном окружении.

## 4. Урок 2. Требования и карта страниц

**Результат:** `docs/brief.md` и `docs/page-map.md`. Это короткие рабочие документы, не подробная спецификация на десятки страниц.

Основные сценарии посетителя:

1. Открыть текущий выпуск с главной.
2. Найти выпуск другого года.
3. Перейти из оглавления в статью и обратно к выпуску.
4. Найти статью по названию, автору или ключевому слову.
5. Узнать требования к рукописи и состав редакции.

Запрос агенту:

```text
Готовим frontend-only сайт вымышленного научного журнала «Контур».
Изучи AGENTS.md. Сохрани docs/brief.md и docs/page-map.md.
Стек: Astro static, TypeScript, CSS; все данные локальные.
Используй карту из курса: главная, архив, выпуск, статья, поиск,
о журнале, редакция, авторам, контакты, 404.
Для каждой страницы укажи цель, блоки, общие компоненты и критерии готовности.
Не добавляй backend, личные кабинеты и новые разделы. Код пока не пиши.
Если есть блокирующая неопределённость, задай один вопрос.
```

Согласуйте одну версию. Для каждого интерактивного элемента определите поведение: ссылка переходит, кнопка меняет состояние, фильтр меняет список. Не оставляйте «потом подключим» для всего интерфейса.

Если CE уже установлен, этот урок можно провести через `/ce-brainstorm`, а затем `/ce-plan`. Это **альтернативный способ**, не дополнительный обязательный круг поверх тех же документов. Подробности: [COMPOUND_ENGINEERING.md](COMPOUND_ENGINEERING.md).

**Стоп-критерий:** каждый раздел имеет назначение; задача не содержит скрытой серверной функциональности.

## 5. Урок 3. Контент до дизайна

**Результат:** типы и единый набор демонстрационных данных. Сначала реальные по длине строки, затем компоненты под них, а не наоборот.

Пример договорённости о данных в `src/data/types.ts`:

```ts
export interface Author {
  id: string;
  name: string;
  affiliation: string;
}

export interface Issue {
  slug: string;
  year: number;
  number: number;
  title: string;
  publishedAt: string;
  description: string;
}

export interface Article {
  slug: string;
  issueSlug: string;
  title: string;
  authorIds: string[];
  category: string;
  publishedAt: string;
  abstract: string;
  keywords: string[];
  sections: { heading: string; paragraphs: string[] }[];
  references: string[];
  image?: { src: string; alt: string };
  pdfPath?: string;
}
```

Даты храните как `YYYY-MM-DD`, для отображения договоритесь об одном формате и явно заданной временной зоне. Не дублируйте одну статью в данных главной, выпуска и поиска: эти страницы выбирают записи из одного источника. Пути к PDF/изображениям должны указывать на существующие файлы.

Запрос агенту:

```text
По docs/brief.md создай src/data/types.ts, authors.ts, issues.ts и articles.ts.
Нужны 4 вымышленных автора, 3 выпуска за 2 года и 12 учебных статей.
Зафиксируй выпуск 2026-01 и статью open-science-review.
Название этой статьи: «Открытая наука: обзор практик».
У неё должны быть ключевые слова «открытая наука».
Подготовь длинный заголовок, несколько авторов и запись без изображения.
У одной статьи будет таблица в шаблоне для проверки переполнения.
Не выдумывай настоящие DOI/ISSN/ORCID, учреждения и научные доказательства.
Проверь уникальность slug и связи authorIds/issueSlug.
Не создавай страницы, API и библиотеки для данных.
```

На первом проходе достаточно подробного текста одной статьи; остальные нужны для сеток, поиска и проверки длины. Не тратьте время на написание двенадцати полноценных псевдонаучных исследований.

**Стоп-критерий:** все связи разрешаются, slug уникальны, длинный контент подготовлен, учебный статус очевиден.

## 6. Урок 4. Визуальная система

**Результат:** утверждённые `docs/design.md` и `src/styles/tokens.css`.

Если макета нет, достаточно 2–3 референсов: один для композиции, один для типографики, один для чтения длинной статьи. Сохраняйте ссылки и коротко записывайте, что именно берёте. Не копируйте целиком чужой сайт и не собирайте бесконечную галерею.

### Дизайн-бриф для журнала

- Характер: научная редакционная площадка, спокойная, ясная, без SaaS-лендинга.

- Акцент: типографика и обложка выпуска, не декоративная анимация.
- Белый фон, тёмный текст, синий акцент; не полагаться только на цвет.
- Основной текст статьи ограничен примерно `65–75ch`.
- На мобильном сначала содержание, затем вспомогательные блоки.
- На первом этапе системные шрифты с кириллицей; собственные шрифты — только при необходимости, локально и с лицензией.

Начальные токены, которые можно уточнить **до** тиражирования страниц:

```css
}
```

Токены не гарантируют контраст во всех сочетаниях: проверьте фактические текст/фон, фокус и disabled-состояния.

Запрос агенту:

```text

читаемые аннотации, без градиентов ради украшения и сложных анимаций.
```

**Стоп-критерий:** одно направление выбрано, мобильный порядок блоков определён. После этого не меняйте стилистику на каждой странице. Если макет уже есть — извлеките его правила вместо придумывания нового дизайна.

```text
│   │   ├── ArticleLayout.astro
│   │   ├── CatalogLayout.astro
│   │   └── ContentLayout.astro
│   ├── data/
```

Это целевая структура, не команда создать все пустые файлы заранее. Дополнительные шаблоны выделяйте при реальной необходимости. Не нужен универсальный компонент на 25 флагов для всех страниц.

### Обязанности слоёв

- `BaseLayout`: `html lang="ru"`, `head`, уникальные title/description из props, общие CSS, ссылка пропуска к содержимому, шапка и подвал.
- Шаблон: композиция статьи, каталога или информационной страницы.
- Компонент: повторяемая карточка, навигация, пустой результат.
- Файл в `pages`: выбирает данные и передаёт их шаблону.
- `scripts`: только клиентские взаимодействия, не backend.

Не создавайте «компонент для каждого div». Выделяйте повторяемые структуры или блоки с самостоятельным поведением.

### Генерация статей без сервера

Файл `[slug].astro` не означает обязательный backend. В статическом Astro заранее перечислите пути через `getStaticPaths()`.

Пример `src/pages/articles/[slug].astro`, когда данные и `ArticleLayout` уже созданы:

```astro
---
import type { InferGetStaticPropsType } from 'astro';
import { articles } from '../../data/articles';
import ArticleLayout from '../../layouts/ArticleLayout.astro';

export function getStaticPaths() {
  return articles.map((article) => ({
    params: { slug: article.slug },
    props: { article },
  }));
}

type Props = InferGetStaticPropsType<typeof getStaticPaths>;
const { article } = Astro.props;
---

<ArticleLayout article={article} />
```

Пример предполагает именованный экспорт `articles` и prop `article` в шаблоне. Приведите импорты к фактическому проекту, не вставляйте код поверх другой структуры вслепую. По тому же принципу генерируются страницы выпусков. Новая запись появляется после повторной сборки — это ожидаемое поведение статического сайта.

Запрос агенту:

```text
Используй @journal-layout, если он установлен, и утверждённый design.md.
Реализуй BaseLayout, шапку, подвал, breadcrumbs и ArticleLayout.
Подключи локальные статьи через getStaticPaths.
Сначала доведи /articles/open-science-review/ до эталонного состояния:
заголовок, авторы, метаданные, аннотация, ключевые слова, текст,
таблица, литература и ссылка к выпуску. Если PDF нет, не рисуй скачивание.
У одной страницы один h1; основной текст не растягивай на всю ширину.
Проверь страницу на ширине 390 и 1440, сохрани скриншоты и выполни npm run check.
Пока не делай остальные типы страниц и не меняй дизайн-направление.
```

Для основного меню договоритесь о доступной кнопке с именем **«Меню»**, `aria-expanded` и `aria-controls`. Выберите один простой вариант: раскрывающийся блок, не модальное окно. Закрытый блок не должен оставлять невидимые ссылки в Tab-порядке. При Escape меню закрывается, фокус возвращается к кнопке. На широком экране навигация видна без нажатия.

**Стоп-критерий:** длинный заголовок и таблица не ломают страницу; шапка, фокус и чтение удобны на узком экране. Только после этого тиражируйте систему.

## 8. Урок 6. Остальные шаблоны и страницы

**Результат:** связный сайт из повторно используемых частей.

Порядок работы:

1. `ArticleCard` и `IssueCard` — один раз проверить длинный заголовок и отсутствие картинки.
2. Страница выпуска — описание и список статей этого выпуска.
3. Архив — список выпусков, пока без клиентского фильтра.
4. Главная — выбранный текущий выпуск и 3–4 статьи из общего набора.
5. Информационный шаблон — о журнале, авторам, редакция, контакты.
6. Поиск — разметка формы и результатов; поведение следующим уроком.
7. 404 — понятный текст и реальные ссылки.

Не делайте весь список одним запросом. Пример задачи на одну итерацию:

```text
Используй существующие стили и компоненты.
Создай IssueCard и страницу /issues/2026-01/ из локальных данных.
Выпуск показывает только свои статьи, каждая ведёт на существующий URL.
Переиспользуй ArticleCard; не копируй её разметку в страницу.
Не меняй главную и ArticleLayout.
Проверь переходы, npm run check и ширины 390/1440.
Покажи результат и остановись.
```

После подтверждения выдайте следующую ограниченную задачу. Информационные страницы можно собрать одной группой: они имеют одну композицию и низкий риск взаимных конфликтов.

### Что должно быть реальным уже в макете

- Внутренние ссылки, хлебные крошки и активный пункт меню.
- Названия и количества, вычисленные из данных, а не случайные числа.
- Уникальные title/description, favicon, понятный порядок заголовков.
- Локальные изображения с размерами и осмысленными `alt`; декоративным — `alt=""`.
- Печатный вид статьи через `@media print`: убрать навигацию, оставить содержание.

Не создавайте ссылку `href="#"` вместо действия. Отсутствующий файл или функциональность обозначайте честно. Канонический URL, sitemap и настоящие издательские метаданные добавляйте после появления домена и проверенных реквизитов, а не с выдуманными production-адресами.

**Стоп-критерий:** из главной можно пройти в архив → выпуск → статью и вернуться; общая оболочка одинакова на всех страницах.

## 9. Урок 7. Локальные взаимодействия

**Результат:** интерфейс выглядит и ведёт себя законченно без серверных запросов.

| Элемент | Что делаем сейчас | Что не делаем |
| --- | --- | --- |
| Мобильное меню | Раскрываем/закрываем локально | Не устанавливаем библиотеку меню |
| Архив | Фильтруем 3 выпуска по году в браузере | Не создаём API |
| Поиск | Ищем по 12 статьям локально | Не подключаем поисковый сервис |
| Оглавление статьи | Ссылки на секции с устойчивыми ID | Не делаем сложный scrollspy |
| PDF | Ссылка только на реально существующий локальный файл | Не генерируем фиктивные загрузки |
| Контактная форма, если нужна | Валидация и честный demo-результат | Ничего не отправляем и не сохраняем |

### Поиск: простая реализация для малого набора

Для курса достаточно заранее вывести 12 карточек в HTML, передать каждой нормализованную поисковую строку через `data-*` и переключать `hidden`. Не загружайте полный текст всех статей в клиентский пакет и не используйте полнотекстовый движок ради двенадцати записей.

Согласуйте контракт:

- Форма имеет `role="search"` или семантически подходящий search-landmark.
- Поле доступно по label **«Поиск по статьям»**, имя query-параметра — `q`.
- Кнопка — **«Найти»**, сброс — **«Сбросить поиск»**.
- Совпадения ищутся по названию, имени автора и ключевым словам без учёта регистра, с обрезкой пробелов.
- Пустой запрос показывает все статьи; несуществующий — сообщение «Ничего не найдено».
- После действия обновляются `?q=...` и счётчик; повторное открытие URL восстанавливает запрос и результаты.
- При изменении URL через History API поддерживается `popstate`, чтобы Back/Forward работали предсказуемо.
- Счётчик можно объявлять через `aria-live="polite"`, но не озвучивать все карточки подряд.
- При отключённом JavaScript остаётся исходный список и пояснение через `noscript`.

Фильтр года делается так же просто: доступны все выпуски без JS, выбор года управляет `hidden`. `display: grid` у карточки не должен переопределять скрытие; при необходимости добавьте явное правило `[hidden] { display: none !important; }` в согласованный слой стилей.

Запрос агенту:

```text
Добавь клиентский поиск на /search/ по контракту курса:
label «Поиск по статьям», кнопки «Найти» и «Сбросить поиск».
Ищи по заголовкам, именам авторов и keywords уже выведенных карточек.
Поддержи ?q=, прямое открытие, перезагрузку и Back/Forward.
Нужны состояния: все результаты, найденные, пустые; без JS — исходный список.
Не используй backend, fetch к API, innerHTML для пользовательского ввода
или новую библиотеку. Проверь запрос «открытая наука» и отсутствие результатов.
Покажи проверенные сценарии и остановись.
```

Не вставляйте запрос пользователя в HTML через `innerHTML`: используйте `textContent`. Не отправляйте содержимое форм во внешние сервисы. Если делаете demo-форму контактов, обрабатывайте submit через `preventDefault()` и пишите «Демонстрация: данные никуда не отправлены», а не «Письмо отправлено». Отдельно проверьте отсутствие сетевого запроса после отправки и безопасное поведение без JS.

**Стоп-критерий:** каждый видимый контрол работает или честно объясняет ограничение; браузер не делает запросов к backend.

## 10. Урок 8. Адаптивность, доступность, визуальная проверка

**Результат:** короткий отчёт `docs/qa.md` с конкретными ошибками и исправлениями.

### Проверять не только скриншоты

| Проверка | На что смотреть |
| --- | --- |
| 360 / 390 px | Меню, длинные слова, кнопки, поля, отсутствие горизонтальной прокрутки страницы |
| 768 px | Переход от одной колонки к нескольким, порядок sidebar |
| 1440 px | Ограничение ширины, ритм, длина строк, отсутствие чрезмерно широких карточек |
| Масштаб 200% | Доступность текста и контролов без перекрытий |
| Клавиатура | Tab/Shift+Tab, Enter/Space, Escape; фокус виден и не теряется |
| Контент | Длинный заголовок, несколько авторов, длинная ссылка, таблица |
| Состояния | Поиск пустой/успешный/без результатов, сброс, выбранный год |
| Сеть и console | Нет пропавших ассетов, ошибок JS и неожиданных внешних запросов |

Ширины — контрольные примеры, не исчерпывающая гарантия адаптивности. Протяните окно между ними; breakpoint выбирается по тому, где ломается контент, а не только по названию устройства.

### Что поручить skill и браузеру

```text
Используй @web-design-guidelines для src/components, src/layouts,
src/pages, src/scripts и src/styles. Сначала выдай краткий список
подтверждённых проблем с file:line, не переписывай весь проект.
Проверь семантику, фокус, меню, формы, контраст, изображения и reduced motion.
Если источник правил недоступен, явно сообщи об этом.
```

Этот skill получает актуальные правила из внешнего источника. Он помогает с аудитом кода, но не заменяет проверку браузером, скринридером и человеком.

Отдельный браузерный проход:

```text
Через Playwright MCP проверь главную, архив, выпуск, статью и поиск
на 390 и 1440 px. Для статьи дополнительно проверь 360 и 768 px.
Пройди путь главная → выпуск → статья, меню клавиатурой,
поиск с результатами/без результатов и фильтр года.
Сохрани скриншоты в artifacts/screenshots/ и фактические результаты в docs/qa.md.
Проверь console и сеть. Не называй оценку Lighthouse реальными Core Web Vitals.
Сначала отчёт; исправляй только согласованные проблемы.
```

Сначала исправляйте поломки и недоступность, затем ритм/отступы, в конце косметику. Не просите «сделать красивее всё» после каждой проверки.

### Правила доступной вёрстки

- `header`, `nav`, `main`, `footer`, понятный один `h1` и последовательные подзаголовки.
- Ссылка перехода к основному содержимому появляется при фокусе.
- У полей есть видимые label, у кнопок с иконкой — доступное имя.
- Ссылки используются для переходов, кнопки — для действий.
- Контраст обычного текста ориентируйте на WCAG AA: не менее 4.5:1; крупного — 3:1. Проверьте также нетекстовые элементы, состояния и фокус по применимым требованиям.
- Интерактивные области не тесные; ориентир для удобства — около 44×44 CSS px, это не универсальное изложение всех исключений стандарта.
- Не скрывайте контент обрезкой ради ровных карточек. Полный заголовок статьи важнее одинаковой высоты.
- Таблицу помещайте в локально прокручиваемую область, не превращайте весь сайт в горизонтальный скролл; область должна быть доступна с клавиатуры.
- Анимацию уменьшайте при `prefers-reduced-motion`; в курсе она почти не нужна.

Для оценки загрузки используйте production preview, локальные изображения адекватного размера и ограниченное число шрифтов. Один показатель Lighthouse не подтверждает полную доступность или скорость у реальных читателей.

**Стоп-критерий:** нет критических проблем навигации и чтения; оставшиеся косметические вопросы перечислены и не блокируют передачу.

## 11. Урок 9. Сборка, регрессия и передача

### Обязательная проверка без дополнительных тестовых библиотек

Остановите dev-сервер через Ctrl+C в его терминале. Из каталога проекта выполните отдельно:

```bash
npm run check
```

```bash
npm run build
```

```bash
npm run preview -- --host 127.0.0.1 --port 4321
```

Проверьте уже **сборку**, а не только dev-режим. Откройте напрямую URL статьи и выпуска, обновите страницу, проверьте поиск с `?q=`, локальные картинки и PDF. Проверьте `/404.html`; обработка произвольного отсутствующего пути зависит также от настроек будущего хостинга.

Не должно быть обязательных обращений к внешним API, шрифтам и картинкам. Для проверки самостоятельности запретите внешние сетевые запросы, сохранив доступ к localhost. Полный offline-режим браузера блокирует и локальный HTTP, поэтому это не тот же тест. Service Worker ради курса не нужен.

### Необязательная автоматизация: когда правок уже много

MCP-проверка — исследовательский проход агента. Для повторяемой регрессии нужны файлы тестов. Если сайт будете развивать, установите Playwright Test:

```bash
npm install -D @playwright/test
```

```bash
npx playwright install chromium
```

На Linux/CI при ошибках системных зависимостей следуйте [официальной инструкции Playwright](https://playwright.dev/docs/browsers#install-system-dependencies); не отключайте sandbox вместо установки библиотек. Chromium для тестов и Chrome, выбранный в MCP-конфигурации, — разные установки.

Создайте `playwright.config.ts`:

```ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  use: {
    baseURL: 'http://127.0.0.1:4321',
    browserName: 'chromium',
  },
  webServer: {
    command: 'npm run preview -- --host 127.0.0.1 --port 4321',
    url: 'http://127.0.0.1:4321',
    reuseExistingServer: false,
  },
});
```

Перед запуском тестов остановите ручной preview/dev на этом порту и выполните сборку. Конфигурация намеренно не переиспользует случайно запущенный dev-сервер.

Пример `tests/journal.spec.ts` под согласованные ранее маршруты и подписи:

```ts
import { test, expect } from '@playwright/test';

test('страница статьи открывается напрямую', async ({ page }) => {
  await page.goto('/articles/open-science-review/');
  await expect(page.getByRole('heading', { level: 1 })).toHaveText(
    'Открытая наука: обзор практик',
  );
  await expect(page.locator('main')).toBeVisible();
});

test('поиск работает с query-параметром и пустым результатом', async ({ page }) => {
  await page.goto('/search/?q=' + encodeURIComponent('открытая наука'));
  const main = page.locator('main');
  await expect(main.getByRole('link', {
    name: 'Открытая наука: обзор практик', exact: true,
  })).toBeVisible();
  await page.getByLabel('Поиск по статьям', { exact: true }).fill('zzzz-no-match');
  await page.getByRole('button', { name: 'Найти', exact: true }).click();
  await expect(main.getByText('Ничего не найдено', { exact: true })).toBeVisible();
});

test('мобильное меню открывается и закрывается', async ({ page }) => {
  await page.setViewportSize({ width: 390, height: 844 });
  await page.goto('/');
  const menu = page.getByRole('button', { name: 'Меню', exact: true });
  await menu.click();
  await expect(menu).toHaveAttribute('aria-expanded', 'true');
  await page.keyboard.press('Escape');
  await expect(menu).toHaveAttribute('aria-expanded', 'false');
  await expect(menu).toBeFocused();
});
```

Это стартовые smoke-тесты, не полный аудит. Если фактические подписи отличаются, согласованно обновите контракт и тесты. Не ослабляйте проверку до «страница просто существует», чтобы получить зелёный результат.

Запуск после сборки:

```bash
npx playwright test
```

Позже добавьте фильтр года, сброс поиска, Back/Forward и проверку внешних запросов. Не начинайте с сотен скриншотных эталонов: сначала стабилизируйте дизайн и окружение.

### Что передать в конце

В `README.md` учебного проекта укажите:

- назначение, ограничения и демонстрационный статус сайта;
- поддерживаемую версию Node и используемый пакетный менеджер;
- установку через `npm ci` при наличии сохранённого `package-lock.json`;
- команды `dev`, `check`, `build`, `preview` и тесты, если добавлены;
- карту страниц и порядок добавления статьи/выпуска;
- где лежат данные, токены, изображения и лицензии;
- результаты проверок и известные ограничения.

Добавление новой статьи должно означать новую запись данных и, при необходимости, её ассеты, а не копию полной страницы с шапкой и подвалом.

Сохраняйте исходники и lock-файл; `node_modules`, `.astro`, `dist` и временные отчёты обычно исключают из Git. Условия хранения скриншотов/эталонов согласуйте отдельно. Публикация не входит в курс: если появится такая задача, настройте статический хостинг, base path при размещении в подпапке и обработку 404.

**Итоговое задание:** добавьте четвёртый выпуск и одну статью, не изменяя шаблоны. Пересоберите сайт и проверьте, что ссылки, архив и поиск учитывают новые данные. Это практическая проверка качества архитектуры.

## 12. Как делать быстрее без потери качества

### Маршрут без лишних кругов

```text
Окружение → короткое ТЗ → локальный контент → одно визуальное направление
→ эталонная статья → общие компоненты → остальные страницы
→ локальные взаимодействия → QA → сборка и передача
```

Если задача маленькая, не запускайте полный Compound Engineering для каждой карточки. Один план для сайта, ограниченные задачи на этап, один целевой аудит после готовности системы. `/ce-work` может включать Git/PR-процесс — заранее ограничьте его, если хотите только локальные изменения.

### Правила экономии времени и контекста

1. **Одна задача — один измеримый результат.** «Сделай архив из IssueCard», а не «сделай весь журнал идеально».
2. **Не более двух направлений дизайна.** После выбора фиксируйте систему; не устраивайте редизайн на каждом этапе.
3. **Проверяйте один насыщенный шаблон рано.** Это дешевле исправления общего дефекта на десяти страницах.
4. **Один источник данных.** Меняйте запись, а не три копии одной статьи.
5. **Сначала структура, потом детали.** Навигация и чтение важнее hover-анимации.
6. **После каждого законченного блока — check и узкий/широкий экран.** Полный аудит не нужен после каждого абзаца.
7. **Исправляйте причину, не маскировку.** Переполнение исправляется у сетки/таблицы, а не глобальным `overflow-x: hidden`.
8. **Документация по конкретному вопросу.** Context7 нужен для проверки API, а не обязательного чтения всей документации перед каждым CSS-изменением.
9. **Один браузерный инструмент.** Не снимайте одинаковые скриншоты тремя MCP.
10. **Короткие отчёты.** Файлы, что проверено, что не проверено, один следующий шаг. Не пересказывайте весь проект после каждого изменения.
11. **Не делегируйте параллельно общий CSS нескольким агентам.** В небольшом сайте интеграция может стоить больше ускорения.
12. **Останавливайтесь по критериям.** После выполнения чек-листа выпишите улучшения отдельно; не добавляйте их автоматически.

### Удобный шаблон запроса

```text
Контекст: frontend-only журнал, Astro static, локальные данные.
Прочитай: AGENTS.md и docs/design.md.
Сейчас нужно: [один шаблон / компонент / сценарий].
Переиспользуй: [существующие файлы].
Не меняй: [границы].
Готово, когда: [2–4 проверяемых условия].
Проверь: npm run check и браузер 390/1440.
Без новых зависимостей, backend, коммитов, push и публикации.
Если заблокирован — покажи причину. После результата остановись.
```

### Как распределить обучение

Ориентир для первого знакомства — 5–8 занятий по 60–120 минут, не обещание точного срока:

- Занятие 1: окружение, skills, браузер и краткое ТЗ.
- Занятие 2: данные и визуальная система.
- Занятие 3: каркас и эталонная статья.
- Занятие 4: выпуск, архив, главная.
- Занятие 5: информационные страницы и поиск.
- Занятие 6: адаптивность, проверки, сборка.
- Дополнительные занятия: устранение пробелов в CSS/HTML, регрессионные тесты.

Если на настройку одного необязательного инструмента уходит всё занятие, отложите его. Не откладывайте при этом базовую браузерную проверку: временно выполните её вручную и честно зафиксируйте это.

## 13. Необязательные расширения

### Context7: только когда нужен справочник

Из терминала в проекте:

```bash
opencode mcp add context7 --url https://mcp.context7.com/mcp/oauth
```

Далее `/mcps` в OpenCode и авторизация при запросе. Пример использования: «Проверь через Context7, как в установленной версии Astro работает `getStaticPaths`; не меняй стек». Подробная настройка и вариант с ключом: [CONTEXT7.md](CONTEXT7.md).

### Playwright CLI вместо MCP: для экономии контекста

Авторы Playwright рекомендуют рассматривать CLI + skill для coding agents: это может расходовать меньше контекста, чем большие MCP-снимки. Когда основной процесс уже освоен, можно **заменить** браузерный MCP на этот путь:

```bash
npm install -g @playwright/cli@latest
```

```bash
playwright-cli install --skills
```

Проверьте созданные skill-файлы и их обнаружение OpenCode; не устанавливайте второй набор вслепую. Проверка CLI:

```bash
playwright-cli open http://localhost:4321
playwright-cli resize 390 844
playwright-cli screenshot
playwright-cli close
```

Это необязательная альтернатива, не третий обязательный тестовый инструмент. Начальные ошибки и неоднозначные команды проверяйте через `playwright-cli --help` и официальный README.

### Chrome DevTools MCP вместо Playwright MCP

Полезен, если есть конкретная проблема с загрузкой, сетью или производительностью. Пример полного отдельного `opencode.jsonc`; в существующем файле добавляйте только нужную запись, а Playwright отключите через `disabled: true`, если переходите на альтернативу:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "servers": {
      "chrome-devtools": {
        "type": "local",
        "command": [
          "npx",
          "-y",
          "chrome-devtools-mcp@latest",
          "--headless",
          "--isolated",
          "--no-usage-statistics",
          "--no-performance-crux"
        ]
      }
    }
  }
}
```

Последние два флага отключают предусмотренные этим инструментом usage statistics и запросы к CrUX. Проверяйте актуальные требования Node/Chrome и флаги перед установкой новой версии.

### Figma MCP: только при реальном макете

Если у вас уже есть макет, получайте контекст конкретного фрейма, а не всего файла. Задача агента — извлечь размеры, токены и ассеты и адаптировать к Astro, не переносить случайный сгенерированный React-код как обязательную архитектуру.

Официальный remote endpoint: `https://mcp.figma.com/mcp`. **Сначала проверьте доступность для вашего клиента и аккаунта:** текущая документация Figma ограничивает подключение клиентами из своего каталога. Нельзя обещать, что OpenCode подключится только потому, что поддерживает MCP. Если доступ не разрешён, используйте экспортированные изображения, спецификацию размеров и локальные ассеты; не тратьте день на обход ограничения.

### Compound Engineering: если уже нужен более строгий процесс

Можно заменить ручное планирование командами `/ce-brainstorm` → `/ce-plan`, затем выполнять утверждённые части через `/ce-work` с явными ограничениями. Не нужно делать оба варианта планирования последовательно.

После действительно полезного открытия `/ce-compound` помогает сохранить вывод. Например: «у hidden-карточек grid переопределял скрытие, а тест обнаружил это только при фильтрации». Обычная правка отступа не требует отдельного документа на страницу.

Установка и поведение: [COMPOUND_ENGINEERING.md](COMPOUND_ENGINEERING.md). Не запускайте `/lfg` для первого учебного макета: автономная отправка результата не соответствует задаче локальной вёрстки.

## 14. Финальный чек-лист

- [ ] Есть согласованные карта страниц и визуальное направление.
- [ ] Все данные локальные, учебный статус виден, реальные научные реквизиты не выдуманы.
- [ ] Шапка, подвал и карточки переиспользуются, а не скопированы.
- [ ] Новые статьи/выпуски добавляются через данные без переписывания шаблонов.
- [ ] Нет API, БД, SSR, авторизации и скрытой отправки форм.
- [ ] Главная, архив, выпуск, статья, поиск, информационные страницы и 404 готовы.
- [ ] Нет пустых `href="#"`, несуществующих PDF и ложных успешных отправок.
- [ ] Меню, поиск, фильтр, сброс, прямые ссылки и Back/Forward проверены.
- [ ] Нет горизонтального переполнения страницы на узком экране; таблицы доступны отдельно.
- [ ] Есть фокус, labels, семантика, alt и адекватный контраст.
- [ ] Проверены длинный контент, пустые результаты, отсутствие картинки и режим без JS.
- [ ] `npm run check` и `npm run build` успешны; непроведённые проверки не названы успешными.
- [ ] Готовый `dist` проверен через HTTP-preview, включая прямое открытие вложенных URL.
- [ ] Ассеты локальные, лицензии понятны, обязательных внешних запросов нет.
- [ ] README объясняет запуск, структуру, добавление контента и ограничения.

**Главная мысль:** скорость даёт не количество skills и MCP, а небольшой согласованный объём, один источник данных, один проверенный шаблон и короткий цикл «сделать → посмотреть в браузере → исправить причину».
